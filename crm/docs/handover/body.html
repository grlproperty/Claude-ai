01Why this is a document, not the app

The one thing this handover has to be straight about before anything else.

A single HTML file cannot be this CRM

The security model is the product. Authorisation lives in PostgreSQL row-level security, on a database role that holds neither SUPERUSER nor BYPASSRLS. Passwords are scrypt hashes the application cannot read. Identity numbers are stored as a masked last-three plus a peppered one-way fingerprint, and are deliberately kept out of URLs, query strings and browser storage. The contact preflight runs as a SECURITY DEFINER function so that a reader who may not see a do-not-contact entry is still told RED.

A file opened from a hard drive has no server, no database, no session and no policies. Every one of those protections would become a button that pretends — which is precisely the “visual mockup with fake functionality” the brief forbids. So this file is the handover: what was built, how to run it, and photographic evidence of it working. The application itself is real code, pushed to the branch.

The working application

Branch claude/loving-feynman-pqh1fu of the repository, under crm/. Next.js 15 and React 19 on PostgreSQL 16, TypeScript throughout in strict mode.

02What it refuses to claim

Eight sentences a property CRM is usually happy to say. This one cannot say any of them, because the database refuses — not because a form is careful.

“Email sent.” “WhatsApp sent.” The CRM opens your own mail application or WhatsApp with the number and the wording ready. You send it. Then you write down what happened.

Enforced by: communications.logged_by_hand is CHECK (logged_by_hand) — the database will not hold a row claiming automatic capture. There is no delivery_status, no read_at and no provider_message_id column anywhere, and a test asserts they do not exist.

“Verified.” A FICA file is verified by a named person on a known date, or it is not verified.

Enforced by: fica_records_verified_needs_a_person — status verified is refused without both verified_by and verified_at. A test proves even the schema owner, with row-level security out of the way, cannot write one.

“Approved.” Somebody with the permission approved it, and their name is on it permanently.

Enforced by: commissions_approved_needs_a_person, plus a separate-approver setting the office can switch on so the person who worked a commission out cannot also approve it.

“Paid.” There is no bank feed. A commission recorded as paid is a person’s record of a payment — which is why the status reads Recorded as paid and never Payment confirmed.

Enforced by: commissions_paid_needs_a_person and commissions_payment_needs_approval. No payment_confirmed, bank_reference or gateway_response column exists, and a test asserts that.

“Earned.” — on a sale that has not registered A concluded sale is not a registered sale. They are months apart and only one of them is money.

Enforced by: transactions_registered_needs_date, and the trigger app.commission_registration_guard, which refuses to invoice or record payment against an unregistered transfer unless the office deliberately switches that off. A test proves the refusal holds against a direct write as the schema owner.

“Portal updated.” “Posted to Instagram.” Marketing status is what somebody in the office recorded, never a confirmation from a portal.

Enforced by: no integration exists to be mistaken for one, and a smoke check greps the property page for any claim that a portal was updated.

“Backup completed successfully.” The CRM takes no backups and cannot verify one. It holds the office’s own written answer on who does and how, clearly labelled as a note somebody typed.

Enforced by: the health page has no green state for backups; a test asserts the check can never read ok.

Finding somebody by their identity number Search refuses an ID number rather than quietly returning nothing, and explains where to look instead.

Why: a search box puts what you type into the address bar, the browser history, the referrer header and the server log. Revealing an ID happens on the profile, by somebody holding PERSON_ID_VIEW, and the audit log records that it was viewed — never the number.

03What is NOT CONNECTED

Each of these has its internal architecture in place and no external credential. The CRM says so on its own system-health page rather than showing a green tick.

Email sendingNot connected Opens your own mail application with the message ready. No mail server, no OAuth, no mailbox sync.
WhatsAppNot connected Opens WhatsApp with the number and the wording ready. You send it and log it.
National Consumer Commission registerNot connected Batches prepared, cost estimated, results loaded by hand. Nothing checked automatically.

Home Affairs, CIPC, deeds office, sanctions and PEP listsNot connected A FICA file records what the office collected and who looked at it against the originals.

04Running it

PostgreSQL 16 and Node 22. Nothing else is required, and nothing phones home.

First run

cd crm
npm install

# Two roles: an owner for migrations, and the application
# role, which has neither SUPERUSER nor BYPASSRLS.
createdb grlp_crm
psql grlp_crm -c "create role grlp_owner login password '...'"
psql grlp_crm -c "create role grlp_app   login password '...'"

cp .env.example .env.local   # then fill it in
npm run migrate
npm run build && npm start

Open the CRM and the first authorised @grproperty.co.za address becomes Management. There is no registration page.

The environment

DATABASE_URLthe application role — the one every request uses
DATABASE_ADMIN_URLthe owner role — migrations only, never a request
SESSION_SECRETsigns session cookies
IDENTITY_PEPPERpepper for the one-way identity fingerprint; as sensitive as the numbers themselves
ALLOWED_EMAIL_DOMAINSgrproperty.co.za
STORAGE_LOCAL_PATHprivate document storage, outside the web root

No secret ever reaches the browser. Documents are served only through a route that checks permission on every request; nothing sits on a public URL.

The gate that every stage had to pass

npm run typecheck   # tsc --noEmit, strict, noUncheckedIndexedAccess
npm run lint        # eslint, zero warnings tolerated
npm test            # 518 tests against a real database as the real app role
npm run build       # production build
npm run smoke -- http://127.0.0.1:3100   # 172 checks in a real browser

05What was built, stage by stage

Ten stages, in the order the brief set. Each one finished the gate above before the next began.

StageWhat it contains
1 · FoundationSchema, two database roles, 49 granular permissions across 5 roles with per-user overrides, row-level security on every table, scrypt passwords, sessions, invitations, an append-only audit log and a separate sensitive-access log.
2 · PeopleOne master record per person. Duplicate detection before creation on name, number and a peppered one-way fingerprint of the identity number. A merge that moves every child record in one transaction and keeps a reversible registry of what moved.
3 · PropertiesOne master record per property. Six status concepts kept apart. Price, mandate, sale and rental history; photos and documents in private storage; marketing kept separate from internal notes.

06How the rules are actually enforced

Hiding a button is not security. Every rule below is checked in at least two places, and the database is always one of them.

Authorisation, five layers deep

  • Interface — a control you may not use is not drawn.
  • Page — every page re-checks its permission on the server, so typing the address is refused too.
  • Action — every server action checks again before it writes.
  • Database — 190 row-level-security policies on the connection the request actually uses.
  • Grants — users.password_hash is outside the column grant entirely; sessions and sign-in attempts are unreadable even to Management and reachable only through SECURITY DEFINER functions.

Identity numbers

  • Stored as a masked last three plus a peppered one-way fingerprint. Duplicate detection works on the fingerprint; nobody reads the number to do it.
  • Never in a URL, a query string, a public page, browser storage, an export, or the audit log.
  • Revealing one needs PERSON_ID_VIEW and writes to the sensitive-access log — which records that it was viewed, not what it said.
  • Search refuses to accept one at all.

Nothing is destroyed

  • Append-only, enforced by trigger: audit log, sensitive-access log, permission history, FICA status history, commission history, export log.
  • Archived rather than deleted: people, properties, entities, documents, tags, commission rules, imports.
  • Released rather than deleted: do-not-contact requests.
  • Suspended rather than deleted: user accounts — so every record stays attributed to whoever touched it.

Everything else the brief asked for

  • Optimistic concurrency on every editable record: “This record has been updated by another user. Please refresh before saving.”
  • One transaction for merges, imports, commission approval and assignment changes.
  • CSV values escaped against formula injection; filenames that cannot escape their directory or break a header.
  • URL import defended against SSRF: off by default, allow-list only, HTTPS only, no credentials, every resolved address range-checked, redirects refused, size and time capped.
  • Same-origin checks on state-changing routes; rate-limited sign-in with lockout; no framework or database error ever shown raw.

07The data model

Two rules above all others, and the schema is shaped around them.

One person, one record. One property, one record.

Somebody who is a seller today, a landlord next year and a buyer after that is one row in people with three client types — never three contacts. Business area (which part of the business deals with them) and client type (what they are to us) stay separate columns, because conflating them is how a CRM ends up with the same family in it four times.

83 tables

Across 13 migrations and 5 557 lines of SQL, applied in order with a checksum guard that refuses a migration edited after the fact.

190 policies

Row-level security on every table. An agent’s query is narrowed by the database, not by a where clause somebody might forget.

205 check constraints

Including every honesty rule in the ledger above. A constraint cannot be bypassed by a new code path.

55 triggers

Reference assignment, row versioning, append-only enforcement, contact-date recalculation, and the commission registration guard.

59 app.* functions

Permission checks, visibility helpers, the merge routines, session handling, and the marketing preflight — each SECURITY DEFINER only where that is the point.

Every reference readable

GRLP-00000001 for a person, GRLP-P-, GRLP-T-, GRLP-C-, GRLP-F-, GRLP-M- — assigned by the database, never by the application.

08How it was verified

Nothing is mocked. Every test runs against a real PostgreSQL database as the real application role, so every policy, grant, constraint and trigger is exercised exactly as it will be in use.

518 tests, 96 suites, 0 failing

Including the ones that matter most: that a constraint refuses a forged “verified” or “paid” even to the schema owner; that an agent cannot read another agent’s records, commission, favourites or notifications; that an import breaks cleanly and leaves nothing behind; that a merge moves every child record; that an export refuses an identity column outright rather than dropping it quietly.

Money has its own suite: exact arithmetic on integer cents, half-away-from-zero rounding, and shares that always add back up to the whole.

172 end-to-end checks, 0 failing

One browser run through the whole daily path: first sign-in, a client, the duplicate caught, a property, a lead, a concluded sale, compliance, an import and its rollback, a logged conversation, a trust, a FICA file verified by a person, a commission approved and then — only after registration — recorded as paid, and the office’s own settings.

10What is deliberately not built

The brief drew a line around version one, and holding that line is part of the work.

  • No Gmail or Microsoft OAuth, and no mailbox sync in either direction.
  • No WhatsApp Business API, and no incoming message capture.
  • No delivery or read status, no provider message IDs, no send APIs and no delivery confirmations — real or otherwise.
  • No portal or social integration, so no listing is ever described as published by the CRM.
  • No register lookups against Home Affairs, CIPC, a deeds office, a credit bureau or any sanctions list.
  • No bank or accounting integration, and therefore no payment the CRM claims to have confirmed.

All six have their internal architecture in place: the tables, the permissions, the workflow and the places a real integration would attach. What they do not have is a credential — and where that is true, the CRM says Not connected rather than pretending.
